DATABASE TOPOLOGY DECISION

All three support PostgreSQL. Prefer separate infrastructure databases where Render provisioning, permissions, budget, and connection limits allow; this isolates cache churn and queue/Cable load. Do not assume aliasing primary/cache/queue/cable to the same DATABASE_URL creates independent physical databases or safely permits repeated schema loading.

For the smallest one-Render-Postgres deployment, an explicit single-database configuration is possible: create Solid tables through ordinary primary migrations, omit separate connects_to declarations, and use the existing primary connection deliberately. This preserves one database service but shares load and transaction/failure behavior with business tables. Benchmark before choosing it. A schema file alone is insufficient to migrate an existing database; include a reviewed upgrade migration path for production, not just fresh-db setup.

Separate-database option requires primary/cache/queue/cable entries in database.yml, connection URLs/provisioning, adapter connects_to settings, infrastructure schema/migration paths, deployment preparation for each database, and CI setup. Single-database option keeps primary URL topology and adds ordinary infrastructure migrations to db/migrate. Choose one design before implementation; don't mix both strategies.

ROLLOUT / REDIS REMOVAL GATES

Prepare databases/tables before switching adapters. Keep Redis available during rollout/rollback. Use a coordinated Cable cutover: Redis and Solid Cable processes do not automatically share broadcasts during a mixed-adapter rolling deployment. Cache cutover is cold; control initial upstream request spikes and test warm-up/stale fallback. Queue cutover changes durability/transactions; avoid losing existing async in-flight jobs on shutdown.

After stabilizing Solid and verifying Render connections/metrics, confirm no other web/worker/cron/preview/environment-group/external app uses REDIS_URL or the Key Value instance. Then remove Redis environment/dependency/configuration references, recheck boot/assets/tests, and remove the external Key Value service as a final separately approved deployment operation. Keep schema/data available for rollback; don't blindly destroy infrastructure databases.

NO REDIS USE FOUND THAT REQUIRES RETAINING IT PERMANENTLY

There is no inspected custom Redis lock/session/stream/counter/Lua protocol that Solid must emulate. This is a feasibility assessment, not a guarantee of equal cache availability/latency. External consumers and operational performance still require evidence. Solid Queue concurrency controls are not a drop-in replacement for arbitrary synchronous application locks; retain existing locking behavior.

TESTS AND RISKS

Run full Rails tests/system tests, Zeitwerk, Brakeman, rubocop, asset precompile, fresh DB setup and existing-DB migration tests. Cover forecast Full/Hourly/Discussion/Alerts/Dual/Radar, OpenWeather cache identities, API auth, home-resort tier caps, subscription restore/sync/downgrades, webhook idempotency, and parking updates.

Cache integration tests must use the actual chosen backend: TTL expiry, fetch/read/write/delete, skip_nil, service-result serialization across deploys, race_condition_ttl under concurrent processes, Directions last-good fallback, cache DB failures, eviction, and upstream request counts. NullStore/MemoryStore tests alone don't establish production equivalence.

Cable tests: cross-process publish/receive, reconnect, isolation/origins, rolling cutover, retention, polling load. Queue tests: persistence after restart, retries/scheduled work, transaction/after-commit behavior, worker startup/shutdown, connection exhaustion, and failed-job visibility.

Main risks: shared PostgreSQL contention/bloat/WAL/backup size, insufficient connection headroom, slower polling vs Redis pub/sub, cache cold starts and upstream cost, cache error semantics, transaction coupling, rolling deploy interoperability, and accidentally activating a worker without its tables. Pool/Render service capacity must be measured rather than assuming deleting Redis saves money without tradeoffs.
